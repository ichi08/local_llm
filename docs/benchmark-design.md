# ローカルAPIの性能テスト

現段階では実装と計測ロジックの確認まで。モデル実機測定は未実施です。
2026-10-03に利用者からモデルテストの承認を得ましたが、まず全体の設計を決める段階です。
以下の4分類・8問は相談用の案です。出力の長さを確認し、設計を決めてから質問リストへ反映して実行します。
候補と根拠は [モデル選定メモ](research/2026-10-03-model-selection.md) を参照。

## 関数の構成

`scripts/benchmark_models.py` は、最初に `MODEL_URLS`、次に `QUESTIONS` を定義しています。
モデルの配布ページではなく、revisionを固定したGGUFファイルの直接URLです。
ファイルサイズとSHA-256も記録し、ダウンロード後と実験開始前に確認します。

## ダウンロード済みモデルの再利用

新しく取得する前に、`models/` と既存キャッシュをローカルで調べます。
Hugging Faceの保存先は `HF_HUB_CACHE`、`HF_HOME`、`XDG_CACHE_HOME` の設定を反映します。
llama.cppとLM Studioの一般的な保存先も候補とし、別の保存先は `--cache-dir` で追加します。
同じファイル名だけでは判断せず、予定している重みのサイズとSHA-256が一致したファイルを使います。
見つかったファイルはその場所からロードし、再ダウンロードや重みのコピーを行いません。
探索とハッシュ確認はAPIの計測時間に含めません。
形式・量子化・内容が異なる重みは別の実験条件として扱います。

[Hugging Faceのキャッシュ構成](https://huggingface.co/docs/huggingface_hub/en/guides/manage-cache)、[保存先の環境変数](https://huggingface.co/docs/huggingface_hub/en/package_reference/environment_variables)。

```bash
python3 scripts/benchmark_models.py download --models minicpm5-1b --cache-dir /path/to/existing/models
python3 scripts/benchmark_models.py run --models minicpm5-1b --cache-dir /path/to/existing/models
```

`download` も一致する取得済みファイルがあれば通信を行いません。
`run` は重みをダウンロードしません。足りない場合は取得方法を案内して終了します。

## 関数と実行基盤

- `find_local_model()`：既存の重みを探索・検証する。通信を行わない。
- `download_models()`：既存の重みを優先し、不足分だけ取得する。実験とは別の操作。
- `load_model()`：モデルごとにllama.cppのAPIプロセスを起動し、ロード完了を待つ。
- `measure_response()`：質問をHTTPで送り、返答と時間を取得する。
- `benchmark_loaded_model()`：warmup、各質問のキャッシュ消去、繰り返しを管理する。
- `run_benchmark()`：モデルとGPU／CPUを順番に切り替え、結果を保存する。

GPUとCPUには同じGGUFとllama.cppを使います。MLXとの基盤差による影響を避けられる設計です。
同時利用は1件、文脈長4,096、CPUスレッド8を初期値とします。
GPUは実デバイスとレイヤー配置を確認し、CPUへフォールバックした測定をGPUとして保存しません。

## 計測の範囲

ロード完了 → warmup → KVキャッシュ消去 → **計測開始：HTTP送信 → 入力処理 → 思考と生成 → 完了通知：計測終了** → 保存 → モデル停止。

- `ttft_seconds`：最初の生成テキストまで。思考が先に出る場合は思考を含む。
- `ttfa_seconds`：最初の回答本文まで。利用者が答えを読み始められる時点。
- `total_seconds`：リクエスト送信からSSEの `[DONE]` まで。
- `generation_tokens_per_second`：サーバーが報告する生成速度。HTTP全体の速度とは異なる。

HTTP接続、入力のトークン処理、推論、出力生成はAPI応答時間へ含めます。
重みの取得・検証、モデルロード、warmup、KV消去、プロセス停止、ファイル保存は含めません。
測定中は出力をコンソールへ逐次表示せず、完了後に表示・保存します。
各質問は新しい会話です。前の回答を引き継がず、同じ質問の繰り返しにもキャッシュを使いません。
OSのファイルキャッシュを一律消去する操作は行いません。モデルをロード済みのAPIを測る実験です。

## 質問と評価

目的は、日本語の投稿作成で「どんな回答を、どれくらい待てば得られるか」を比較することです。
要約・翻訳・解説・自由創作の4分類を同じ件数で用意します。各2問、計8問を初回の案とします。
1問だけで分類全体の性能を判断せず、通常の課題と、失敗が表れやすい課題の両方を含めます。
日本語の限られた用途についての実験で、一般的な知能や投稿の拡散率を測る試験ではありません。

### 出力形式の案（相談中）

要約・解説・自由創作は、日本語120字以内の短文1つ。前置き、ハッシュタグ、絵文字は指定しません。
翻訳は英語→日本語を基本とし、短い原文の意味を省かないことを優先します。文字数上限を設けません。
これは実験で決める文章の長さで、Xの文字数カウントを検証する機能ではありません。
記事の本文にも使う200〜400字の回答を中心にする選択肢について、利用者へ確認中です。

### 8問の候補

各課題に原文、依頼文、採点で見る点を保存します。以下は新しい質問リストの候補です。

1. **要約／重要情報の圧縮**：架空の社内検索「灯」。社員20人、試験で検索時間の中央値12秒→5秒、回答の正確さは未評価。120字以内で、改善点と未評価の点を含む紹介文を作る。人数、数値、未評価を保持できるかを見る。
2. **要約／条件と不確実性の保持**：架空のメモ「今週はGPUで試験した。CPUの結果は来週測る予定。待ち時間はまだ集計していない。社外への提供は未定」。120字以内で、現在分かることと今後の予定を伝える。『CPUでも高速』『提供予定』など、資料にない断定を追加しないかを見る。
3. **翻訳／自然な紹介文**：`The local API answers on this computer. No prompts are sent to external services, but other apps may still use the network.` を自然な日本語へ訳す。APIと他のアプリの区別、否定・留保を保持できるかを見る。
4. **翻訳／技術文の意味**：`I could run the model, but I have not measured its response time yet. A smaller file does not necessarily mean a faster reply.` を日本語へ訳す。『起動できた』と『速度を測った』を区別し、not necessarilyを保持できるかを見る。
5. **解説／初心者向けのたとえ**：資料「量子化は重みの数値精度を下げ、容量を減らす方法。回答品質に影響し得る。実行時には重み以外のメモリも使う」をもとに、初心者へ120字以内で身近なたとえを1つ使って説明する。たとえの分かりやすさと、メモリ・品質を断定し過ぎないかを見る。
6. **解説／数字の読み方**：架空のログ「最初の回答本文が2秒後、全文完了が8秒後、ロードは10秒で計測外」をもとに、API待ち時間とロード時間の違いを初心者へ120字以内で説明する。2秒と8秒の意味を混同せず、ロード10秒を加えないかを見る。
7. **自由創作／短い物語**：『雨』『夜』『図書館』を使い、最後に小さな意外性がある120字以内の架空の物語を作る。語句の使用、まとまり、意外性を評価する。
8. **自由創作／紹介投稿**：ローカルLLMが店員をする架空の喫茶店の紹介文を120字以内で作る。『メモリ』『コーヒー』を使い、親しみやすいユーモアを含める。発想と文章の自然さを評価する。架空の設定を追加することは創作として認める。

### 採点の案

各回答は次の3軸を0〜2点、合計6点で採点します。0点は目的を満たさない、1点は修正が必要、2点はそのまま使える程度を目安にします。

- **課題の品質**：要約は重要情報と資料への忠実さ、翻訳は意味の保持、解説は正確さと初心者への伝わり方、自由創作は発想とまとまり。
- **日本語**：自然で読みやすいか。
- **指示への適合**：必要な情報・語句・長さ・出力形式を守るか。

要約・翻訳で情報を作り足すことと、自由創作で架空の設定を作ることは別の基準で採点します。
重大な意味の反転や根拠のない数値は、理由と該当箇所も記録します。
文字数は改行を含む本文全体の `len(answer)` とし、指定語句の有無とともに自動確認できます。
忠実さや面白さは、まず人間がモデル名を伏せて評価します。これらの採点処理はまだ実装していません。

利用者の希望により、速度は各質問5回を既定とします。同じseed 42で行い、品質の採点対象は事前に1回目と決めます。
良い回答だけを選び直さず、全回答と採点理由を残します。同じseedでもCPUとGPUで本文が一致するとは仮定しません。
創作の出力のばらつきを調べる場合は、別seedによる追加実験として分けます。
打ち切り、本文なし、起動失敗は完成した回答の速度・品質の集計から除き、件数と出力を公開記録へ残します。
分類ごとに品質と待ち時間を示し、総合点だけで用途別の違いを隠さない構成とします。

**実装との対応**：現行の `QUESTIONS` は旧案の汎用8問です。4分類の案が決まるまで差し替えていません。

## 対象と進め方の案

基本4モデルをGPU、小さい3モデルをCPUで測るので、7通りのモデル・デバイスの組み合わせです。
8問を各5回なら280応答。warmupはこの数にも計測値にも含めません。
Qwen3.8-27B xhighは、まずIQ2_SのGPU起動と短い応答を試します。同じ8問を5回完了できるなら40応答を追加します。
IQ3_XXSはメモリに余裕がある場合の追加条件とし、基本4モデルのQ4と同じ量子化として扱いません。

1. 出力形式、課題、採点、思考設定、対象モデルを決める。
2. 小さい1モデルで各分類1問・各1回をGPU／CPUで疎通する。完成する出力上限とログを確認する。
3. 条件を固定して基本4モデルを本測定し、品質を採点する。
4. 27B xhighを挑戦枠として検証し、失敗した場合も条件と理由を残す。
5. 待ち時間、回答の比較、CPUで使える範囲、27Bの結果を記事にまとめる。

短文生成でも思考トークンを使うため、API出力上限は本文の文字数とは別です。
本測定の候補は2,048トークンですが、疎通で決めてから固定します。27Bで変更した場合は別条件として明記します。
GPU／CPU間では同じ重み、質問、生成設定、出力上限を使います。
電源接続、他の重い処理の停止、メモリ・スワップの前後確認を行い、実行順も記録します。

## 思考モードと条件

`--thinking auto` は各モデルの既定値、`off` / `on` は切り替え可能なモデルへ明示します。
LFM2.5-2.6Bは公式に常時思考モデルとされているため、含める場合は `auto` を使います。
Qwen3.8の挑戦枠は `reasoning_effort=xhigh` と思考有効を明示し、公式推奨のサンプリングを指定します。
その他の基本モデルは固定の共通設定（temperature 0.7、top_p 0.8、top_k 20、repeat_penalty 1.0）です。
これは今回の比較用設定で、各モデルの最適設定を検証したものではありません。
実際に送った設定を各行の `request_settings` に保存します。

出力上限は思考と本文を合わせて数えます。512トークンは短い動作確認の初期値です。
`finish_reason=length` は `truncated`、本文なしは `no_answer` と記録し、完成した回答の統計から除外します。
失敗件数は併記します。途中打ち切りの速さを成功として比較しないためです。
思考が長いモデルは上限を増やして再測定します。xhighを指定しても、強い量子化と短い文脈・出力上限ではAAのスコアを再現した検証にはなりません。

同じモデルのCPU／GPU比較では設定を統一してください。
モデル間ではトークナイザーが異なるため、tokens/sだけで日本語の速さを判断せず、同じ質問の待ち時間と回答内容を比較します。
各質問5回の中央値・平均・標本分散・標準偏差を出します。少数の標本からp95を主張しません。
記事用には質問と機種を明記し、モデルの実行順を変えた追加測定で熱や他のアプリの影響を確認します。

## 統計の定義

モデル・デバイス・質問ごとに集計します。難易度や入力長が異なる質問の時間を混ぜて分散を出しません。
全文完了まで、最初の生成まで、最初の回答本文までの時間と、サーバー報告の生成速度について次を保存します。

- **中央値**：5回の値を並べた中央の値。代表的な待ち時間を見る。
- **平均**：合計を成功した測定回数で割る。遅い応答の影響も含めた待ち時間を見る。
- **標本分散**：平均からの差の2乗を合計し、測定回数から1を引いた数で割る。時間の単位は秒²。
- **標準偏差**：標本分散の平方根。時間の単位は秒で、ばらつきの大きさを読みやすくする。
- **各回の値と有効件数**：5回すべての成功値、失敗・打ち切りの件数を残す。

分散の `ddof` は1。成功が2回未満なら分散と標準偏差は `null` とし、0で安定しているように見せません。
成功がない場合は中央値・平均も `null` です。失敗や途中の打ち切りを短い応答として平均へ混ぜません。
生成速度の分散の単位は (tokens/s)²、標準偏差は tokens/s です。
固定seedの繰り返しなので、ここでは主に実行時間のばらつきを見ます。創作の多様性を測る値とは区別します。

## 実行手順

Python 3.10以上、curl、llama.cppのサーバーが必要です。
Pythonの追加パッケージは不要です。macOSなら実行基盤の導入候補は次のコマンドです。

```bash
brew install llama.cpp
llama-server --version
llama-server --list-devices
```

`llama-server` がなく `llama` が入る配布なら、スクリプトは `llama serve` を使います。
現在の公式CLI仕様を参照して実装していますが、このPCでの実モデルとの結合確認は次の段階です。
バージョンによる非対応フラグは、起動ログで確認して調整します。
[llama.cpp公式サーバー仕様（参照commit）](https://github.com/ggml-org/llama.cpp/blob/4ebdf2c74acce30883d8e34b7c70b3eb8146f2fe/tools/server/README.md)

以下は現行コードの動作を確認するコマンドです。設計が決まるまではモデル取得・実行を進めません。
新しい4分類への差し替え時には質問IDも更新します。

まず計画を表示し、小さい1モデルだけで疎通します。

```bash
python3 scripts/benchmark_models.py plan
python3 scripts/benchmark_models.py download --models minicpm5-1b
./setup.sh --output .local/hardware-before-benchmark.json
python3 scripts/benchmark_models.py run --models minicpm5-1b --questions explain json --devices gpu cpu --thinking off --repeats 1
```

基本4モデルのGPUと、小さい3モデルのCPUを比較する場合：

```bash
python3 scripts/benchmark_models.py download
python3 scripts/benchmark_models.py run --max-tokens 2048
```

PCを操作せず測定する場合、macOSでは実行中のアイドルスリープを抑止する形で起動します。
テストの回答や進行状況はファイルへ逐次保存するので、終了後に確認できます。

```bash
caffeinate -i python3 scripts/benchmark_models.py run --max-tokens 2048
```

GPUのないサーバーでは `--devices cpu`。実行基盤とCPUの違いを含む別実験として記録します。
MacのCPU測定から、任意のサーバーの速度は推定できません。

Qwen3.8-27Bは既定のダウンロード・測定対象に含めず、挑戦枠を明示して実行します。

```bash
python3 scripts/benchmark_models.py plan --models qwen3.8-27b-iq2-s
python3 scripts/benchmark_models.py download --models qwen3.8-27b-iq2-s
python3 scripts/benchmark_models.py run --models qwen3.8-27b-iq2-s --questions reasoning --devices gpu --max-tokens 2048 --repeats 1
```

まずメモリとスワップを確認して起動・短い応答を試し、余裕があればIQ3_XXS版を選んで比較します。
Qwen3.8もCPUで試す場合は `--devices cpu --all-cpu` を明示します。
モデル順を変える場合は `--models` の順番を使います。

## 保存されるもの

`.local/benchmarks/実行日時/` に保存します。

- `results.jsonl`：各モデル、デバイス、質問、繰り返しごとの応答・思考・時間・失敗。
- `summary.json`：モデル・デバイス・質問ごとの完成回答の各回の値、有効件数、中央値、平均、標本分散、標準偏差と失敗数。
- `metadata.json`：重みURLとSHA-256、runtimeのバージョンとハッシュ、設定、コードcommitと未コミット状態。
- モデルごとの `.log`：起動やGPU配置の調査用ログ。

実測ファイルにはローカルの絶対パスも含み得るので、生成物はGit対象外です。
記事用の記録には必要な値を抽出し、初回PC情報や電源状態、アプリ状態、メモリとスワップの前後も記入します。
CLIは失敗・打ち切りがあれば終了コード1を返します。結果ファイルは残します。

## 実装を確認する

```bash
python3 -m unittest discover -s tests -v
```

疑似APIで計測範囲、思考と本文の区別、打ち切り、キャッシュ、GPUフォールバックを確認します。
これらのテストの秒数は模擬値で、LLMの性能データではありません。
